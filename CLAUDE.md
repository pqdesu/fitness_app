# Fitness app

A simple workout tracker in Ruby on Rails. The owner's own description of the core use: "I go to the gym, log my workouts and what I did for the day, and then that's it."

The full project context (product brief, every decision, data model, page flows, current state, open issues) is in [doc/Prompt/project-context.md](doc/Prompt/project-context.md). Read it before making product or design choices.

## Product rules

- Top priority is a very intuitive, simple, user-friendly UI: few taps and little typing to log a set on a phone at the gym.
- Plain POST and GET: record entries, read them back. Do not add features beyond what is asked.
- Keep the planning layer (splits, workout days, planned exercises), the shared exercise catalogue and the admin role. Do not propose removing them.
- Users pick an exercise from the catalogue or create their own; only an admin changes the shared catalogue.
- An admin is a normal user with two extras: managing the shared catalogue, and managing users (make or unmake an admin, delete a user). An admin can also create private exercises; one goes to the catalogue only when they tick "Add to the shared catalogue".
- Equipment is chosen per lift: free weights, or a machine whose brand the user types.
- The split page is the plan: the workouts on the week and the exercises of each, nothing more. Only the split page changes the plan.
- A workout day's page is the workout. It lists the planned exercises and those added while training; "Add exercise" there adds to that day's workout only, never to the plan. Sets (weight, then reps) are added when the user opens an exercise.
- Removing an exercise from a workout keeps it on the plan if it was planned; if not, it is gone.
- There is one logged workout per workout per day. Sets added from any split join it, and Legs and Lower count as the same workout.
- A split has one logged workout per day. A second workout on the same day only comes from another split.
- An exercise is on a workout day once and in a logged workout once.
- A workout can be moved to another day for the current week only (today to Saturday). The split's plan is never changed by a move, and the next week follows the plan again. Moving onto a day that has a workout swaps the two.
- Sets added from a workout day go to the date that workout falls on this week (its weekday, or the one it was moved to). Wednesday's workout opened on Thursday fills in Wednesday; a workout later this week takes no sets yet. "Start workout" and "Train as extra" open it on today.
- "Start workout" alone creates nothing. A split's workout is logged when its first set is added, when an exercise is added to it from its page, or when its timer is started; a workout that is not in the split is logged when its first exercise is added. With the automatic timer on (Account settings, `users.timer_auto_start`), opening today's workout starts it: it is logged with no exercises and its timer runs (owner, 2026-11-20).
- The workout timer is Start, then Pause and Resume, and Stop (owner, 2026-11-20: "make it paused and resume", then "keep the stop button"). `workout_logs.started_at` is the first start, `paused_at` when it is paused (empty while it runs), `ended_at` when it was stopped for good, and `paused_seconds` adds up the time between each Pause and Resume, left out of the recorded time. Only those are saved; the page counts the time in between. It starts on today's workout only; once started it pauses, resumes and stops on any day, past midnight too, and the workout stays on its own date (owner, 2026-11-20: a paused workout must resume after midnight). While paused, the paused time counts up on screen from the saved pause; Resume adds that difference to `paused_seconds`. Recorded and paused times are exact to the second, never rounded ("1 h 24 min 7 s"). While the timer is paused, adding an exercise or a set asks whether to keep it paused or resume it (Keep paused / Resume), and leaving the workout page by a link whether to keep it paused or stop it (Keep paused / Stop timer) (opening the workout's own exercises is not leaving); either answer then carries on, closing the box cancels (owner, 2026-11-21). A timer left running is corrected from History: its pen opens "Edit timer", where the finish is chosen in hours and minutes (seconds 0); a time earlier than the start is the next day, and a timer still running or paused stops there. A stopped timer is done; one paused and never stopped ends at its pause. It shows start ~ end, the recorded time and the paused time; past midnight each time shows its date as a badge (11:30 PM [20/11] ~ 1:00 AM [21/11] · 1 h 20 min · paused 10 min).
- A workout trained on a day its split has nothing on that week is a rest day workout. It is marked when logged (`workout_logs.rest_day`) and the mark is never recalculated.
- Weights keep three decimals (1.125 kg).

## How to work in this repo

- Run every session on the `opusplan` model (`/model opusplan`; owner, 2026-11-23): Opus thinks and plans in plan mode, then Sonnet implements once the plan is approved. Plan each feature or fix in plan mode first. A sub-agent that implements runs on Sonnet or Haiku (`model: "sonnet"` or `"haiku"`). If the session is not on `opusplan`, tell the owner at the start.
- Work in a git worktree under `.claude/worktrees/<branch>`, on a branch named for the work (`git worktree add .claude/worktrees/<branch> -b <branch> master`). The owner asked for this on 2026-11-16, replacing the earlier "no worktrees" rule. Leave the main checkout alone: it is the owner's.
- A server started from the main folder serves the main folder's branch, not the worktree. To let the owner see the work before merging, run a server from the worktree on another port and say which, or give them the command to check the branch out. Do not finalize work unprompted.
- The worktree and the main folder share one development database. Say so before running a migration that drops or renames something `master` still reads.
- Ruby 3.3.13 (through rbenv) and PostgreSQL are installed natively on the owner's machine. Run the tests, the server and migrations directly (`bin/rails test`), not in Docker. If either is missing, tell the owner instead of skipping the tests.
- Never edit a test file just to make a failing test pass. Write tests that check exactly the behaviour asked for; once written, a failing test means the app code is wrong: fix the code and keep working until `bin/rails test` passes. If a test contradicts what the owner asked for, ask before changing it.
- Look at changed pages in a real browser at phone width before calling UI work done. The tests do not run the JavaScript or show the layout.
- When asked to finalize, finish or wrap up a branch, use the `finalize-branch` skill (in `.claude/skills/`). It writes a detailed change doc to `doc/<branch>.md`, pushes, and opens a pull request.
- Never merge a pull request, enable auto-merge, or run `git pull` / `git merge` for the owner. Give them the commands instead; they decide what goes into `master` and what comes into their folder.
- Branch names are a few plain lowercase words joined by dashes, with no digits and no `claude/` prefix.
- Before committing or pushing a branch, update the base data with the `update-seed-data` skill (`.claude/skills/`), so `db/seeds/data.yml` carries the latest data and keeps the old. `finalize-branch` does this as one of its steps.
- Change docs must be very detailed: every step, decision, file changed, the reason, and how it works now.
- Open and resolved issues are tracked in [doc/Issues/Issues.md](doc/Issues/Issues.md). When an issue is fixed, move it under "Issues Resolved". Risks a branch knowingly leaves behind go under "Potential issues", saying which branch they come from.
- When asked to read, investigate or explain issues from `Issues.md` (usually one section, on `master`), use the `investigate-issues` skill (`.claude/skills/`). It traces each issue to its cause and explains it without changing anything, then asks before fixing.
- When asked to read, plan or explain how to build features from [doc/Features/Features.md](doc/Features/Features.md), use the `plan-features` skill (`.claude/skills/`). It reads the code each feature touches and explains how to build it without changing anything, then asks before building.

## Stack and commands

Ruby 3.3.13, Rails 8.1, PostgreSQL, Devise 5, Bootstrap 5 with SCSS (Dart Sass through dartsass-sprockets), Hotwire (Turbo and Stimulus) through importmap, simple_form, Minitest.

```bash
bin/setup                 # gems and database
bin/rails db:seed         # admin user, starter catalogue, then db/seeds/data.yml (idempotent, only adds)
bin/rails seed:dump       # merges the dev database's real data into db/seeds/data.yml (keeps the old)
bin/rails server
bin/rails test
bundle exec rubocop       # linter; must report no offenses
bundle exec brakeman      # security scan of the code; must report no warnings
bundle exec bundler-audit check --update  # known vulnerabilities in the gems
bin/rails mock:last_week  # logs last week's sessions for every split, as mock data
bin/rails mock:clear      # deletes the mock workouts and the plans the mock task added
```

`.github/workflows/ci.yml` runs the tests, rubocop, brakeman and bundler-audit on every push.

`MAILER_SENDER` sets the address password-reset emails come from.

## Code map

- Program: `Split` has many `WorkoutDay` (one per weekday, name from a fixed list) has many `WorkoutExercise`.
- Record: `WorkoutLog` (belongs to the user, survives split deletion) has many `WorkoutLogExercise` has many `WorkoutSet`.
- `Lift` concern (`app/models/concerns/lift.rb`) is shared by planned and logged exercises: name copy, equipment, machine brand.
- `Exercise` without a user is in the shared catalogue; with a user it is that user's own. A name is unique within the catalogue and within one user's own exercises.
- `WorkoutDayMove` (workout day, `week_start`, weekday) is a workout on another weekday for one week. `Split#week_plan(date)` is the one place that answers what is on which day that week (the plan with that week's moves); the dashboard, the Today box and the rest day mark read it. `Split#move_for_week!` writes moves and swaps; creating a workout day or changing a weekday clears the split's moves.
- `WeekMovesController` (`POST` and `DELETE /splits/:id/week_move`) moves a workout for this week and goes back to the plan. The Splits pages show the plan; only the dashboard passes `plan:` to `splits/_week`.
- `WorkoutSummary` (plain Ruby, `app/models/workout_summary.rb`) totals loaded logs: workouts, exercises, sets, top weight. It needs logs loaded with `includes(workout_log_exercises: :workout_sets)`.
- `LoggingDate` (controller concern) gives the date a workout day's pages log on: `?date=`, which those pages pass along, or else `WorkoutDay#date_in_week_of(today)`. A future date shows no add-set form, and `WorkoutLog` refuses it.
- `WorkoutExercise#entry_on!(date)` is the one way sets of a planned exercise reach a log: it finds or creates the user's session of that workout on that date, and the entry of that exercise in it.
- The plan is edited on `splits#show`: one card per workout day (`#day-<id>`), each with its own picker (`shared/_exercise_picker` with `key:`, opened by `exercise_picker_button(css, key:)`), posting to `workout_exercises#create`; plan actions return to that card. `workout_days#show` is the workout: its picker posts to `workout_log_exercises#create` with `workout_day_id` and `date`, which adds entries to that date's session (creating it), and an extra entry links to its logged workout.
- `ExercisePicker` (controller concern) reads the "Add exercises" modal and decides whether a new exercise is private or shared. In that modal an admin has an × on every exercise (a `turbo_method: :delete` link, since the rows sit inside the "Add selected" form); `ExercisesController#destroy` goes back to the page it came from (`redirect_back_or_to`). `Paginated` (controller concern) with `shared/_pagination` pages History, the catalogue and the users list.
- `Admin::UsersController` (`/admin/users`) is the admin's users page, linked from the user menu.
- A set is a `<tbody>` of its own in a set table (`workout_sets/_set`): the row of numbers, then its note, or the note field with Save and Cancel while editing (`row_edit_controller.js`).
- The dashboard calendar (`pages/_calendar`) and the week strip (`splits/_week`, with `states:` on the dashboard and Today pages only) say how each day stands (`Dashboard#calendar_states`, `#week_states`, through `DayStates`, owner 2026-11-24): a day of the plan (with that week's moves) from today on, or once trained, is filled blue (`is-planned`); a planned day that passed with nothing logged is dotted (`is-missed`, only from the first workout ever logged); a workout off the plan is a light ring (`is-extra`); today has a ring around it. Every day has a tooltip (`CalendarHelper#day_title`), and a missed day is a link to its plan's workout on that date (`workout_day_path(day, date:)`, found by `DayStates#day_on`) to log a forgotten workout; a day with no plan is never a link (owner, 2026-11-24). Pointing at any day draws a halo. "Logged" is `WorkoutLog#logged?` (an exercise added or the timer started), so a workout left with nothing in it is not logged and `WorkoutSummary#workouts` does not count it. A logged day links to that workout, or to `/workout_logs?date=YYYY-MM-DD` when the day has several.
- The dashboard calendar's month name folds it (Bootstrap collapse, `#calendar-body`) and its "Month" link opens `pages#month` (`GET /dashboard/month`): the month's totals (`pages/_summary_tiles`, shared with "This week"), each split's share (`Dashboard#month_by_split`) and each exercise's sets and heaviest weight (`WorkoutSummary#by_exercise`), with the calendar again (`foldable: false`).
- The dashboard's Today box (`pages/home`, `pages/_lifts`) shows today's sets once there are any, with "last time" as a link; before that it shows last time's heaviest sets. Its button is "Start workout", then "Continue".
- On a rest day the Today box opens a panel: one pill per workout name of the split, each with a pop-up (`pages/_rest_day_start`) to move it to today or train it as an extra, and pills for the fixed workouts the split does not have, which open `workout_logs#new`.
- The active split card has "This week" (`pages/_week_overview`), "Move a workout" (`pages/_move_workout`) and "Back to the plan". Recent workouts are dropdowns (`pages/_recent_workout`). All of these use Bootstrap collapse and modals, with no JavaScript of their own.
- Deleting a workout opened with `?from=dashboard` returns to the dashboard, otherwise to History.
- An admin renames an exercise from a workout day: the pencil opens `exercises#edit` with `workout_day_id`, which is where saving or cancelling returns.
- The muscle group of an exercise is chosen from `Exercise::MUSCLE_GROUPS` (or left empty, "Other"); it is never typed.
- Sub-pages declare their back button with `<% back_to path %>` at the top of the view; the layout draws it as a round arrow. It returns to the page visited before (`back_trail.js` keeps each tab's pages in sessionStorage, `back_controller.js` follows it), skipping form pages (`body[data-back-skip]` on new, edit, create, update) and a record deleted from its own page. `path`, the parent page, is only the fallback when the tab has no earlier page.
- Flash messages (`shared/_flashes`, `flash_controller.js`) are cards at the top of the screen. A notice fades out after 5 seconds, waiting while it is pointed at or focused; an alert stays until its × is pressed. Every `data-turbo-confirm` opens the app's own box (`shared/_confirm`, `confirm_dialog.js`, through `Turbo.config.forms.confirm`), never the browser's `confirm()`. It sits above another open modal (`_confirm.scss` z-index).
- Dates follow the browser's time zone, sent in a cookie by `app/javascript/time_zone.js` and remembered in `users.time_zone` for sessions that have not reported one yet.
- `Dashboard` (plain Ruby, `app/models/dashboard.rb`) answers everything the home page shows for a user on a date; `PagesController#home` only builds it. It also keeps `logs_count` and `sets_count`, which no box shows now (the owner asked to keep them).
- A controller finds a record through its owner: `current_user.workout_exercises`, `.workout_log_exercises` and `.workout_sets` (`has_many through` on `User`). `WorkoutLog.session_of(workout, date)` is the one lookup of a session; `WorkoutDay#log_on(date)` uses it. `Split#rest_day?(date)` is the one rest day check.
- Controllers read form fields with `params.expect(model: [:field])` (Rails 8), and models tidy text with `normalizes` rather than a `before_validation`. Rubocop enforces the hash shorthand (`where(date:)`).
- The "once only" rules also have unique indexes; `ApplicationController` rescues `RecordNotUnique` (a double tap) with a message. `from_dashboard?` and `errors_of(record)` are there too, for controllers and views.
- Accounts: Devise `:lockable` (10 wrong passwords, 15 minutes), passwords of 8 or more characters, `paranoid`. The only admin cannot delete their account (`User#last_admin?`, `Users::RegistrationsController`).
- The content security policy is in `config/initializers/content_security_policy.rb`. A new outside host (fonts, scripts, images) must be added there or the browser blocks it. Do not add inline `style=` attributes or inline scripts.
- The workout timer box is `workout_logs/_timer`, on a workout day's page and a logged workout's page. `WorkoutTimersController` corrects its finish from History (`GET /workout_logs/:id/timer/edit`, `PATCH /workout_logs/:id/timer`, through `WorkoutLog#finish_at`), starts or resumes it (`POST /workout_days/:id/timer` or `/workout_logs/:id/timer`), pauses it (`POST /workout_logs/:id/timer/pause`) and stops it (`DELETE /workout_logs/:id/timer`); `timer_controller.js` runs the clock. The paused-timer alert is `workout_logs/_timer_alert` with `timer_alert_controller.js`, on a workout day's page, a logged workout's page (both `leave: true`) and the exercise page: it asks before elements marked `data-alert-when-paused="add"` (the picker button, add-set forms, the log page's Add buttons) and before links outside `[data-stays-in-workout]`. The automatic timer is the page pressing Start itself (`auto_submit_controller.js`), never a GET that writes, because Turbo prefetches links on hover. `workout_time(log)` writes "6:02 PM ~ 7:15 PM · 1 h 3 min · paused 10 min" for History and Recent workouts, through `time_parts`, which keeps each part whole with the "·" after it so no line starts with a separator. The box leads with a status pill (Running, with a breathing dot; Paused; Finished; the card carries `is-idle`, `is-running`, `is-paused` or `is-finished`), the clock is dimmed while paused, and on a phone Pause/Resume and Stop take a full-width row.
- The add-set form and the set table are `workout_sets/_form` and `workout_sets/_table`, used by the exercise page and the logged workout page.
- Styles: `components/` for what pages share, `pages/` for one page; `application.scss` lists them in one order.
- `db/seeds/data.yml` is the base data (users, splits, logged workouts), matched by email, name, weekday and date, never by id. `lib/seed_data/` writes it (`Dumper`, `Merge`: the file only grows) and loads it (`Loader`: creates what is missing, changes nothing that exists). Mock workouts are never written.
- Equipment: an admin keeps the equipment catalogue (`EquipmentItem`, `Admin::EquipmentItemsController`, `/admin/equipment`); each lift picks free weights, a machine or bodyweight in `shared/_equipment_fields`. A bodyweight set's weight is added to or taken off the body (± button, `sign_controller.js`). An exercise can be unilateral.
- Set tags: an admin keeps them (`SetTag`, `Admin::SetTagsController`, `/admin/tags`); a set carries them through `WorkoutSetTag`. Add set has the tag pills, and each set has a Tag button. `users.auto_warm_up` ticks Warm-up on each exercise's first set.
- An exercise's note for the day is its logged exercise's `notes`, written on the exercise page once it has a set. Notes save with the blue arrow (`.note-save`), and the focus ring wraps the box and the arrow.
- Lists of exercises fold with `shared/_list_toggle`. Logged exercise cards fold, and `fold_controller.js` keeps a card open across a Turbo morph. Edit and delete sit in a ⋯ menu (`ActionsMenuHelper`: `actions_menu`, `menu_link`, `menu_button`, `menu_delete`), and delete is an ×.
- Order: `Positioned` (`app/models/concerns/positioned.rb`) gives `move!(to)` ("up", "down" or a place, 1 first) to `WorkoutExercise` and `WorkoutLogExercise`. A row is numbered only once its list is reordered; `position` is nullable and NULL sorts last in PostgreSQL. `PATCH .../move` with `to`. The lists are ordered `position, id`, never by id alone.
- Drag and drop: `sortable_controller.js` (SortableJS, vendored by importmap). Items carry `data-sortable-url` and a `.drag-handle`. A drop sends a hidden Turbo form, and the page morphs with the moved row lit up (`flash[:moved]`, `.just-moved`). Two lists of one `group` move items between them through `data-sortable-into-url` (with `-method` and `-confirm`); the item goes back at once and the server decides.
- A workout day's page is two cards: "In this workout" (the session's exercises in its order, draggable) and "Still to do" (the plan's exercises not in it yet, in plan order). Dragging a to-do row in adds it where dropped (`workout_log_exercises#create` with `to`). Dragging a planned row back takes it out of the workout and asks first if it has sets. An exercise added while training cannot go to "Still to do". A day to come shows only the plan.
- Cardio: an exercise of the Cardio group (`Exercise#cardio?`, `muscle_group == "Cardio"`; no column of its own) is logged as rows of incline, speed and time (`CardioEntry`, `cardio_entries`, `CardioEntriesController`, `cardio_entries/_table`, `_entry`, `_form`) instead of sets, and has no equipment (its `equipment_label` is "Cardio"). The exercise page and a logged workout's cards switch on `cardio?`. `WorkoutSummary#cardio_seconds` and the helpers `sets_and_time`, `summary_counts` and `entry_done` put its time where sets are counted. `SeedData::Cardio` carries the rows in `db/seeds/data.yml`.
- Cardio timer (owner, 2026-11-24): a cardio exercise has its own timer where a lift has its rest timer (`cardio_entries/_timer`), on the two rest columns of its logged exercise (`rest_started_at`, `rest_ended_at`; an exercise is cardio or lifts, so they never clash) and through `RestTimersController`. A planned exercise with nothing logged starts it through `POST /workout_exercises/:id/rest`, which logs the workout. Idle, it offers Start cardio timer or Add manually (opens the folded form; earlier days show the form). Stop puts its time in the Add form (`WorkoutLogExercise#timer_seconds`); while it runs the form keeps incline and speed and its button is "Stop and add" (the row takes the timer's time), a typed time still wins, and `CardioEntriesController#create` clears the timer. A Cardio workout opens its first exercise, and a cardio exercise with a timer started stays open. Leaving the page while it runs asks through `rest_alert_controller.js` ("cardio"). A Cardio workout has no workout timer (`workout_logs/show`).
- Cardio workout: on a rest day the Today box has a Cardio button beside Start workout, to `workout_logs#new` with `workout=Cardio` (`WorkoutLog::CARDIO`; a logged workout name only, never a split day, so `WorkoutLog::WORKOUTS` and not `WorkoutDay::NAMES`). There `ExercisePicker#picker_scope` lists and accepts only cardio (`cardio_workout?`, set by `WorkoutLogsController` and `WorkoutLogExercisesController`), and `shared/_exercise_picker` with `cardio: true` asks only a name.
- Rest timer: Start rest and Stop (`RestTimersController`, `POST`/`PATCH`/`DELETE /workout_log_exercises/:id/rest`, `workout_sets/_rest_timer`) run on the logged exercise (`rest_started_at`, `rest_ended_at`). The next set takes the rest (`WorkoutLogExercise#take_rest!`) into `workout_sets.rest_seconds`, shown above the set (`rest_text`). An earlier day types it in whole minutes (`rest_approx`, "~3 min"); a set's Edit corrects it. `workout_sets/_rest_alert` (`rest_alert_controller.js`) asks before Add set or leaving while a rest runs. It is rendered before the paused-timer alert so that it asks first, and each asks once. It never touches the workout timer.
- Integration tests are in `test/integration/*_flow_test.rb`, one file per area, on the shared `FlowTest` setup in `test/test_helper.rb`; the dashboard object by `test/models/dashboard_test.rb`; the mock task by `test/tasks/mock_task_test.rb`.
